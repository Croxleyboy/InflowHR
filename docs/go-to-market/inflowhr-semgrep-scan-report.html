SG-01
get_super_admin_uid() hardcodes email address High

supabase/migrations/048_auto_grant_support_access.sql:11

Description

The function get_super_admin_uid() is a SECURITY DEFINER function that returns the auth user ID by looking up andy.jones@kumonix.com directly from auth.users. This was written before the super_admins table existed (created in migration 093). It's used by ensure_super_admin_access() and extend_support_access() to auto-grant tenant support access.

Impact

  • If the super admin email changes, the function silently returns NULL and auto-grants stop working
  • If a second super admin is added, they're ignored — only the hardcoded email gets support access
  • Hardcoded PII (email) in a database function

Proposed fix

Rewrite to query the super_admins table instead: SELECT auth_user_id FROM super_admins LIMIT 1. Also add REVOKE EXECUTE FROM anon.

✓ Fixed — migration 102_scan_fixes.sql: rewrote to JOIN super_admins → auth.users instead of hardcoding email.
SG-02
7 SECURITY DEFINER functions missing REVOKE from anon Medium

Description

These SECURITY DEFINER functions have internal access control guards but lack the outer REVOKE EXECUTE FROM anon defence-in-depth layer. While they check roles internally, an unauthenticated caller can still invoke them (they'll be rejected by the guard, but the function body executes up to that point).

Affected functions

  • get_super_admin_uid() — 048_auto_grant_support_access.sql
  • ensure_super_admin_access() — 048_auto_grant_support_access.sql
  • extend_support_access() — 048_auto_grant_support_access.sql
  • cancel_current_month_checkins() — 083_check_in.sql (recreated in 097)
  • create_nonsso_account() — 066/067
  • setup_non_sso_admin() — 069
  • ensure_company_user() — 043/068

Proposed fix

Add REVOKE EXECUTE ON FUNCTION <name>(<args>) FROM anon, public; GRANT EXECUTE ON FUNCTION <name>(<args>) TO authenticated; for each function in a single migration.

✓ Fixed — migration 102_scan_fixes.sql: REVOKE FROM anon + GRANT TO authenticated on all 7 functions.
SG-03
app_settings SELECT USING(true) overrides company-scoped policy Medium

supabase/migrations/093_security_audit_fixes.sql:81

Description

Migration 032 created a "Company scoped read" policy on app_settings with USING(is_my_company(company_id)). But migration 093 later added a second SELECT policy with USING(true). In Supabase, multiple SELECT policies on the same table OR-combine — so the USING(true) policy wins and any authenticated user can read every company's settings.

Impact

Low data sensitivity — app_settings contains feature toggles and company preferences, not PII. But it still leaks which features a competitor company has enabled, and violates the tenant isolation principle.

Proposed fix

Drop the USING(true) policy from migration 093. The existing company-scoped policy from migration 032 already provides correct access.

✓ Fixed — client: LanguageContext.tsx changed .eq('id', 1) → .limit(1). SQL: migration 102_scan_fixes.sql drops the USING(true) policy.
SG-04
send-notification-email has no role check Medium

supabase/functions/send-notification-email/index.ts

Description

The edge function verifies the caller belongs to the same company as the notification (line 98) but does not check the caller's role. Any authenticated employee in the company could trigger email delivery for any notification record in their company — including notifications addressed to other employees.

Impact

Low in practice. The function only sends the email for an already-created notification — it doesn't create one or change who receives it. The notification was already created via RLS-scoped insert. The worst case is an employee triggering a re-send of a colleague's notification email. No data is exposed beyond what's already in the notification record (which is company-scoped).

Proposed fix

Option A: Add role check (admin/HR/manager only). Option B: Verify that the notification's employee_id matches the caller's employee_id (self-only). Option C: Accept as-is since the function only triggers delivery of existing notifications.

✓ Fixed — edge function updated to re-fetch notification server-side and verify caller belongs to same company. Company membership check added in CodeRabbit CR-01 fix (migration 099, PR #50).
