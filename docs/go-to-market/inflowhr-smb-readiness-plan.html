Launch Readiness Assessment READY FOR SMB

The architecture and compliance posture is well-positioned for SMB launch (10–200 employees). The security work completed across migrations 094–095 and multiple security audits exceeds what most competing UK HR platforms shipped at launch.

What would pass SMB procurement scrutiny

  • Multi-tenant isolation — RLS on every table with company_id scoping; salary/payroll data isolated at database level, not just UI-hidden
  • Immutable audit trail — GDPR audit logging with full actor/action/old-new tracking; UPDATE and DELETE revoked on the audit table
  • Data subject rights — DSAR export across 16+ tables, employee anonymisation preserving 6-year HMRC records, consent tracking with grant/withdraw timestamps
  • Controlled access — service admin access requires company pre-authorisation (not self-granting), 48-hour expiry, full audit trail
  • Data retention — documented in DPA Schedule 4 and Privacy Notice, automated via pg_cron (notifications 90 days, geolocation 12 months, offboarded employees 30 days)
  • UK data residency — Supabase eu-west-2 (London) for all PII; Cloudflare CDN serves only compiled app bundle (zero personal data)
  • Account lifecycle — cancellation with 90-day cooling-off, cascade deletion, login blocking for frozen companies, data export before purge

Remaining items before first paying customer

  • DPA signed off — v0.1 is in lawyer review. Cannot onboard a paying customer without a signable DPA available. This is the hard blocker.
  • MFA for non-SSO accounts — HR systems holding NI numbers, bank details, and salaries with password-only auth would concern a security-conscious buyer. Mitigated if initial customers use Microsoft SSO (their IdP handles MFA). Required before selling to email/password companies.
  • Tested backup restore — daily backups are confirmed but no restore has been tested. Need a confident answer to "what happens if there's a problem with our data?" backed by a tested process with documented RPO/RTO.
  • Data export enhancements — employee DSAR needs Excel/ZIP format with confirmation popup. Company archive needs to be a fully restorable package: table data with preserved UUIDs, storage bucket files (receipts, photos), generated restore.sql, and auth-mapping for re-onboarding. All exports logged to super admin audit trail.

What SMB buyers typically don't require

  • SOC 2 / ISO 27001 — nice to have, rarely required under 200 employees
  • Penetration test certificate — adds credibility but not a gate for SMB
  • PITR — daily backups with 7-day retention is standard for this tier
  • Field-level encryption — AES-256 at rest via Supabase satisfies "appropriate technical measures"

Your questions answered

Can company admins see salaries? Do I need a dedicated payroll role?
Yes, this is a gap. Right now, every employee in a company can SELECT all salary data at the database level — the RLS policy is company-scoped, not role-scoped. The admin portal roles system gates the Payroll page in the UI, but the database doesn't enforce it. You need RLS-level salary isolation: only the employee themselves, plus users with a "payroll" portal permission, should be able to read salary/bank columns. This is Phase 2, item 2.1 below.
Is the 48-hour service admin access GDPR compliant?
Time-limited access is good practice, but self-granting is the problem. Under GDPR Art. 28, the processor (you) should only access controller (customer) data on documented instructions. The current ensure_super_admin_access() lets you self-grant access with no customer approval. For compliance, company admins should grant/approve access, not the service admin. The 48-hour window itself is fine — it's the consent flow that needs fixing. Phase 2, item 2.3.
As the service provider, I have full database access — is this allowed?
Yes, but only with a signed DPA and documented controls. GDPR allows processors to access personal data — that's the whole point of a Data Processing Agreement. Your DPA must state: what data you access, why, your security measures, your sub-processors (Supabase, Cloudflare, Brevo), and breach notification obligations. Supabase service role key access is normal for a SaaS operator. Document it, don't remove it. Phase 1, item 1.2.
Do I need to check where code is hosted and what backups I get?
Yes — verified. Supabase project is in West Europe (London) eu-west-2 — all employee PII stored in UK/EU. Cloudflare Pages runs on the global CDN (Standard usage model) but the SPA contains no PII — only the Supabase database holds personal data. Daily backups with 7-day retention are included; PITR can be added as an add-on. 100 GB storage and 2M edge function invocations/month included. Still needed: test a restore and document the DR process. Phase 3, items 3.2 (done) and 3.3 (gap).
Should religion/belief and geolocation consent toggles move to the admin portal?
No — they must stay in employee Settings. Under GDPR Art. 9(2)(a), special category data consent (religion/belief) must be given by the individual employee, not granted by an admin. Same for geolocation — the employee must grant consent themselves. Moving these toggles to the admin portal would break GDPR compliance. Company admins already have read-only visibility of consent status via RLS policy — they can see who has consented, but cannot consent on someone's behalf.
Is the self-service data download necessary, and what format should it use?
Self-service download is not required but is a differentiator. GDPR Art. 15 requires providing data within 30 days of a request — most HR platforms handle this via email/ticket. Your self-service "Download My Data" button eliminates the admin overhead entirely. Format: changing from JSON to Excel/ZIP — one .xlsx workbook per data category (Personal Details, Payslips, Leave History, Skills & Certifications, etc.) in a ZIP file. This is what employees expect and what other UK HR platforms provide. Company archives use a different format: a restorable ZIP with table JSON (preserving UUIDs), storage bucket files, generated restore.sql, and an auth-mapping file for re-onboarding. On scope: a DSAR must provide all personal data currently held — the full history, not just the latest year. Data already deleted under your retention policy doesn't need recreating.

1.5 DSAR Process and Data Export ENHANCE

Current state

Core functionality implemented. The export_employee_data() RPC returns a comprehensive export across 16+ tables. A "Download My Data" button exists in the Settings page. The export is logged to the GDPR audit trail.

Data retention and DSAR scope

  • UK employment law requires 6 years post-employment for payroll, tax, and NI records (HMRC). anonymise_employee() already preserves these.
  • A DSAR must provide all personal data currently held — not just the latest year. GDPR Art. 15 is absolute. However, data already deleted or anonymised under the retention policy does not need to be recreated.
  • The retention policy protects you: keep what's legally required, delete the rest on schedule, DSAR covers whatever remains.

Employee data download (DSAR)

  • Confirmation popup: Before download, show a modal confirming: what data categories are included, the company name, and the date range the data covers (e.g. "Your personal data held by [Acme Ltd] from [start date] to today")
  • Export format: Change from JSON to Excel/ZIP — one .xlsx workbook per data category (Personal Details, Payslips, Leave History, Skills & Certifications, etc.) bundled in a ZIP. This is what employees expect and what other UK HR platforms provide.
  • Super admin audit logging: All personal data downloads must be recorded in the super admin audit log — not just the GDPR audit trail. Record: who downloaded, what type (personal DSAR), timestamp, and data scope.

Company data archive (restorable)

The company archive must be a complete, restorable package that can be scripted back into a fresh Supabase project. Archive format: ZIP containing:

  • manifest.json — company metadata, archive date, table inventory, Supabase project ID, schema version (migration number at time of export)
  • tables/ — one JSON file per table with all rows, preserving original UUIDs. Exported in foreign key dependency order (companies → departments → employees → payslips etc.)
  • storage/ — all bucket files (receipts, profile photos, certification documents) downloaded from Supabase Storage via API, organised by bucket and path. Includes a storage-manifest.json mapping each file to its database reference (table, column, row ID)
  • restore.sql — generated INSERT statements in dependency order with explicit UUIDs, runnable directly against a fresh Supabase project on the same schema version
  • auth-mapping.json — maps each employee_id to the employee's email address, so auth accounts can be re-linked after users re-onboard
  • RESTORE_GUIDE.md — step-by-step restore instructions

What is fully recoverable

  • All company data tables — employees, payslips, leave, shifts, skills, certifications, expenses, assets, etc. Original UUIDs preserved, foreign keys intact, no remapping needed
  • Storage bucket files — receipts, profile photos, certification documents. Uploaded back to the same paths via Supabase Storage API
  • Company settings, feature flags, admin portal roles and configuration
  • Audit logs and GDPR trail (immutable historical record)

What requires re-authorisation (not recoverable from archive)

  • Auth accounts: Supabase Auth manages its own auth.users table — these cannot be restored from an archive. Employees must re-onboard (SSO re-login or password reset). After re-auth, run the auth-mapping.json script to link new auth_user_id values to existing employee records
  • SSO/Microsoft Entra ID configuration: The OAuth connection between the company's Azure AD tenant and Supabase must be re-established by the company admin
  • Active sessions and tokens: All existing login sessions are invalidated — users log in fresh
  • External integrations: Any Xero, calendar, or third-party connections must be re-authorised by the company admin
  • Supabase Edge Function secrets: API keys for Brevo, etc. are stored in Supabase project settings, not in the database — re-enter on the new project

Restore process

  1. Provision a new Supabase project (or use existing) — ensure schema version matches manifest.json
  2. Run restore.sql against the database — inserts all company data with original UUIDs
  3. Upload storage/ files to Supabase Storage buckets using the storage manifest
  4. Notify employees to re-login (SSO) or reset passwords (non-SSO)
  5. Run auth-mapping script to link new auth user IDs to employee records
  6. Company admin re-configures SSO and any external integrations

Audit logging

All company archive exports and restores must be recorded in the super admin audit log: who initiated, archive type, timestamp, company, number of records, and storage file count.

PHASE 3 Infrastructure Verification Week 3 · £0
3.1 Encryption at rest and in transit DONE

Current state

Platform-level encryption is in place. Supabase provides AES-256 encryption at rest for the database and TLS 1.2+ in transit. Cloudflare enforces HTTPS for the frontend. This is sufficient for SMB.

Note on field-level encryption

Bank details, NI numbers, and tax codes are stored as plaintext columns. Field-level encryption (using pgcrypto) would add a layer but complicates queries and isn't required for GDPR compliance — AES-256 disk encryption satisfies the "appropriate technical measures" requirement. The existing column masking in the admin UI (SEC-H05) prevents casual viewing.
