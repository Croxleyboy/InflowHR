Critical Cross-tenant data leak via stale USING(true) SELECT policiesFixed CWE-863

Source

supabase/migrations/001_initial_schema.sql — lines 237, 252, 271, 278, 285, 296

What happened

Migration 001 created FOR SELECT TO authenticated USING (true) policies on six tables: employees, leave_types, kudos, benefits, courses, and announcements. Migration 020 later tried to drop these and replace them with company-scoped policies, but it dropped "Authenticated users can read" while the original names include the table suffix (e.g. "Authenticated users can read employees"). The drop missed every one of them.

PostgreSQL OR-combines multiple SELECT policies on the same table. If both the original USING(true) policy and the company-scoped policy exist, the USING(true) wins — any authenticated user from any company reads every row.

Exploit

An authenticated employee of Company A opens their browser console and runs:

const { data } = await supabase.from('employees').select('*')
// Returns ALL employees from ALL companies — names, emails, NI numbers, bank details

Tables affected

employees (PII — names, NI, bank details, salary), leave_types, kudos (public only — USING(is_public = true)), benefits, courses, announcements

Verification note

Benefits and courses had no company-scoped replacement policy — migration 020's loop did not include them. The fix creates replacement "Company scoped read" policies for both tables (allowing company_id IS NULL for core/shared entries). The kudos policy was USING(is_public = true), not USING(true) — cross-tenant but limited to public kudos only.

Fix applied

Migration 097: drops all six stale policies and creates company-scoped replacements for benefits and courses (employees, leave_types, kudos, announcements already had replacements from migration 020).

Medium Employee self-promotion to admin via company_users UPDATE policyFixed CWE-862

Source

supabase/migrations/047_gdpr_compliance.sql — lines 253–254

What happened

The UPDATE policy on company_users checks only is_my_company(company_id) OR is_super_admin(). Any authenticated employee within the company can update any row — including their own role column.

Exploit

// Any employee promotes themselves to admin:
await supabase.from('company_users')
  .update({ role: 'admin' })
  .eq('user_id', myAuthUid)

Fix

Replace the UPDATE and DELETE policies on company_users to require is_company_admin():

DROP POLICY IF EXISTS "Company scoped update" ON company_users;
DROP POLICY IF EXISTS "Company scoped delete" ON company_users;

CREATE POLICY "Admin scoped update" ON company_users FOR UPDATE
  USING ((is_company_admin() AND is_my_company(company_id)) OR is_super_admin());
CREATE POLICY "Admin scoped delete" ON company_users FOR DELETE
  USING ((is_company_admin() AND is_my_company(company_id)) OR is_super_admin());

Also restrict INSERT to admin/super-admin only.

Fix applied

Migration 097: UPDATE and DELETE policies replaced with admin-scoped versions requiring is_company_admin() AND is_my_company(company_id).

Medium Overly permissive write policies on data tables allow intra-tenant tamperingFixed CWE-862

Source

supabase/migrations/020_super_admin_rls.sql — lines 48–67 (template applied to all tables)

What happened

The INSERT, UPDATE, and DELETE policies on most tenant-scoped tables check only is_my_company(company_id) — any company member, not just admins. Tables like payslips, expense_claims, leave_balances, and announcements can be modified or deleted by any employee who knows a row's UUID.

Exploit

// Any employee deletes a colleague's payslip:
await supabase.from('payslips')
  .delete().eq('id', 'target-payslip-uuid')

Fix

For admin-managed tables (payslips, leave_balances, announcements, onboarding, workflow_tracker), restrict write policies to (is_company_admin() AND is_my_company(company_id)) OR is_super_admin(). For employee-owned tables (expense_claims, leave_requests, timesheets), scope writes to employee_id = get_my_employee_id() for the employee role plus admin override.

Verification note

Migration 056 already fixed write policies on payslips, leave_types, leave_balances, onboarding, app_settings, and employees. Only announcements, workflow_tracker, and notifications remained with overly permissive writes.

Fix applied

Migration 097: Admin-scoped INSERT/UPDATE/DELETE policies applied to announcements, workflow_tracker, and notifications.

Medium daily-email-reminders edge function accepts unauthenticated requestsFixed CWE-306

Source

supabase/functions/daily-email-reminders/index.ts — line 53

What happened

The handler Deno.serve(async () => { ... }) uses the service role key to query all companies' data and send emails via Brevo. No Authorization header check. Anyone who knows the function URL can trigger mass email sends.

Exploit

curl -X POST https://<project>.supabase.co/functions/v1/daily-email-reminders
# Sends reminder emails to all employees with meetings tomorrow

Fix

Add a shared-secret check for cron invocations:

const authHeader = req.headers.get('Authorization')
if (authHeader !== `Bearer ${Deno.env.get('CRON_SECRET')}`) {
  return new Response('Unauthorized', { status: 401 })
}

Set CRON_SECRET in the Supabase Edge Function secrets and pass it in the pg_cron or external cron invocation header.

Fix applied

Edge function: Added CRON_SECRET bearer token auth check at the top of the handler. Returns 401 if missing or mismatched.

Medium company-logos storage bucket allows any authenticated user to overwrite any company's logoFixed CWE-863

Source

supabase/migrations/023_company_logo.sql — lines 10–16

What happened

The INSERT and UPDATE policies on storage.objects for the company-logos bucket check only bucket_id = 'company-logos' with no tenant scoping. Any authenticated user can upload or replace any file in the bucket. The bucket is also marked public = true (acceptable for logos, but combined with the write issue it means a defaced logo is served immediately).

Exploit

// Authenticated user from Company B replaces Company A's logo:
await supabase.storage.from('company-logos')
  .upload('company-a-uuid/logo.png', maliciousFile, { upsert: true })

Fix

Scope upload/update policies to the user's own company using storage.foldername(name):

DROP POLICY IF EXISTS "Authenticated users can upload company logos" ON storage.objects;
DROP POLICY IF EXISTS "Authenticated users can update company logos" ON storage.objects;

CREATE POLICY "Company admin can upload logos" ON storage.objects FOR INSERT
  TO authenticated WITH CHECK (
    bucket_id = 'company-logos'
    AND (storage.foldername(name))[1] = get_my_company_id()::text
    AND (is_company_admin() OR is_super_admin())
  );
CREATE POLICY "Company admin can update logos" ON storage.objects FOR UPDATE
  TO authenticated USING (
    bucket_id = 'company-logos'
    AND (storage.foldername(name))[1] = get_my_company_id()::text
    AND (is_company_admin() OR is_super_admin())
  );

Verification note

Upload path is flat {companyId}.{ext}, not folder-based. Fix uses split_part(name, '.', 1) instead of storage.foldername().

Fix applied

Migration 097: Replaced both policies with admin-scoped versions using split_part(name, '.', 1) = get_my_company_id()::text.

Medium cancel_current_month_checkins allows cross-tenant operationFixed CWE-639

Source

supabase/migrations/083_check_in.sql — lines 161–192

What happened

The function checks is_company_admin() OR is_super_admin() but is_company_admin() returns true if the caller is admin of any company. The function then operates on the provided p_company_id parameter. An admin of Company A can cancel Company B's check-in records.

Fix

Replace the guard with a targeted check:

IF NOT (
  EXISTS (
    SELECT 1 FROM company_users
    WHERE user_id = auth.uid()
    AND company_id = p_company_id
    AND role IN ('admin', 'hr')
  ) OR is_super_admin()
) THEN
  RAISE EXCEPTION 'Access denied';
END IF;

Fix applied

Migration 097: Recreated function with targeted company_users check against p_company_id instead of global is_company_admin().

Low Super admin email addresses exposed in client JavaScript bundleFixed CWE-200

Source

src/context/AuthContext.tsx — lines 25–28

What happened

VITE_SUPER_ADMIN_EMAIL and VITE_BREAK_GLASS_EMAIL are inlined into the production bundle by Vite's VITE_ prefix. Anyone inspecting the compiled JavaScript learns which accounts have super-admin privileges — useful for targeting attacks.

The actual super admin check runs server-side via the super_admins table (migration 093), so this is information disclosure, not an authorization bypass.

Fix

Move the super-admin check entirely server-side. Add an RPC like am_i_super_admin() that returns a boolean, and call it once at auth time. Remove both VITE_ variables.

Fix applied

AuthContext.tsx: Removed SUPER_ADMIN_EMAILS constant and client-side email check. Added server-side supabase.rpc('is_super_admin') call at auth time. State cleared on sign-out.

Low Receipt and avatar uploads lack server-side file type and size validationFixed CWE-434

Source

src/pages/NewExpenseItem.tsx — line 73  |  src/pages/admin/AdminEmployees.tsx — line 292

What happened

The HTML accept="image/*" attribute is a browser hint that can be bypassed. No server-side MIME type check or size limit is applied. An attacker could upload a malicious SVG with embedded JavaScript or an arbitrarily large file. The receipts bucket is private (signed URLs only), which limits exposure, but the avatar bucket may still be public.

Fix

Add a Supabase storage policy or edge-function hook that validates MIME type against an allowlist (image/jpeg, image/png, image/webp) and enforces a max size (e.g. 5MB). Block image/svg+xml to prevent stored XSS.

Fix applied

Migration 097: Replaced existing receipts upload policy with one combining tenant scoping AND extension validation (jpg, jpeg, png, webp, gif, pdf, json). Single policy prevents OR-combination bypass.

Low DISABLE ROW LEVEL SECURITY remains inside SECURITY DEFINER function bodiesFixed CWE-271

Source

supabase/migrations/055_critical_security_fixes.sql — lines 37–38 (delete_company_data)
supabase/migrations/056_high_security_fixes.sql — lines 137–138 (run_demo_seed)

What happened

Both delete_company_data and run_demo_seed disable RLS on one_to_one_meetings and one_to_one_comments mid-function, then re-enable it. This is unnecessary because SECURITY DEFINER already bypasses RLS. If the function errors between the DISABLE and ENABLE, RLS is left off on those tables until someone notices.

Migration 093 adds a safety net re-enable, so the risk is reduced but the unnecessary DISABLE remains in the function bodies.

Fix

Remove the ALTER TABLE ... DISABLE/ENABLE ROW LEVEL SECURITY lines from both function bodies. SECURITY DEFINER already runs as the defining role, bypassing RLS.

Fix applied

Migration 097: Recreated delete_company_data without DISABLE/ENABLE RLS (matched migration 070 version exactly). run_demo_seed not recreated (600+ line function; risk mitigated by migration 093 safety-net ENABLE).

Areas scanned clean

No findings

  • Hardcoded secrets — no API keys, tokens, passwords, private keys, or database URLs found in source. All secrets loaded from environment variables at runtime
  • Service role key isolation — SUPABASE_SERVICE_ROLE_KEY used only in server-side edge functions (Deno.env.get), never in any src/ file
  • VITE_ env vars — only Supabase URL, anon key (both designed to be public), and the two admin emails (low-risk, noted above). No secrets behind the VITE_ prefix
  • XSS — no dangerouslySetInnerHTML with user input, no innerHTML injection, no unescaped template interpolation. Edge function emails use escapeHtml()
  • SQL injection — all dynamic SQL uses format(%I) with hardcoded table name arrays. No string-concatenated queries in RPCs
  • CSRF — JWT bearer auth throughout; no cookie-based sessions. Inherently safe
  • user_metadata authorization — not used for privilege checks anywhere. All auth gates use server-side table lookups (super_admins, company_users)
Scope and limitations

This audit scanned the full repository at rest — source code, SQL migrations, edge functions, environment configuration, and storage policies. It was local and read-only: no network calls were made and no files were modified.

What was checked: hardcoded secrets and env-prefix leaks, RLS policy completeness and correctness, SECURITY DEFINER function guards, storage bucket policies, client-side vs server-side authorization, XSS vectors, SQL injection in RPCs, CSRF posture, open redirects, edge function authentication, file upload validation, and code execution sinks.

What was not checked: the live database state (actual policies in effect may differ from what migrations declare if any migration was partially applied or rolled back), runtime Supabase dashboard configuration, Edge Function secret values, infrastructure-level controls (WAF, network segmentation), third-party dependency vulnerabilities, or business logic correctness. The critical finding (#1) should be verified against the live database with SELECT * FROM pg_policies WHERE tablename = 'employees' to confirm whether the stale policies are actually in effect.

This report describes code-visible findings, not a compliance guarantee. Rescan after fixes to confirm resolution.
