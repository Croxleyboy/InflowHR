CR-03
is_company_admin() is global — cross-tenant write on companies/company_users Already Fixed
supabase/migrations/001_multi_tenant.sql : line 84
CodeRabbit finding

The is_company_admin() helper checks only whether the caller is an admin of any company, not the target company. Policies on companies and company_users (from migration 018) use this global result, allowing a tenant admin to modify or delete another tenant's company rows.

Validation

Already fixed. Migration 097 (security audit v2) replaced the companies and company_users write policies with versions requiring is_company_admin() AND is_my_company(company_id). The combination of both checks ensures the caller must be admin of the specific target company. The delete_company_data RPC was also locked to is_super_admin() only (migration 055 + 097).

UX / service impact

None — fix is already live. Company admins can still manage their own company as before.

Decision: SKIP — no action required Finding refers to migration 001/018 code. The vulnerability was remediated by migration 097 which adds the is_my_company(company_id) guard to all write policies. Verified in current codebase.

Findings requiring correction
CR-01
send-notification-email IDOR — trusts client-supplied payload Needs Fix
supabase/functions/send-notification-email/index.ts : line 94
CodeRabbit finding

The function validates only that the bearer token belongs to some user, then trusts payload.record entirely. The browser-side caller (sendNotificationEmail in src/lib/supabase.ts) builds the record client-side. Any authenticated user can craft a request with arbitrary employee_id, title, and message to: (a) target any employee in any tenant, (b) send phishing emails with InflowHR branding, (c) suppress genuine notification emails by marking them as sent.

Validation

Confirmed — issue exists in current code. The edge function at supabase/functions/send-notification-email/index.ts still reads payload.record directly from the request body with no server-side re-fetch or company verification.

UX / service impact

UX impact: minimal. The fix changes the edge function's internal logic only. The client-side caller already sends record.id in the payload — the fix simply ignores the rest of the payload and re-fetches the authoritative record server-side. No visible change to users.

Service impact: positive. Prevents cross-tenant phishing and notification suppression. The email_sent flag update will now only apply to verified records.

Proposed fix

Accept only the notification ID from the payload. Re-fetch the full record server-side with the service role client. Verify the notification's company_id matches the caller's company via company_users lookup. Apply send_email/email_sent checks against the authoritative record. Constrain the employee lookup by company_id.

// Accept only notification ID, re-fetch server-side
const notificationId = payload?.record?.id ?? payload?.notification_id
const { data: record } = await supabase
  .from('notifications')
  .select('id, title, message, link, employee_id, company_id, send_email, email_sent')
  .eq('id', notificationId)
  .single()

// Verify caller belongs to same company
const { data: caller } = await supabase
  .from('company_users')
  .select('company_id')
  .eq('auth_user_id', user.id)
  .eq('is_active', true)
  .maybeSingle()

if (!record || !caller || record.company_id !== caller.company_id) {
  return new Response(JSON.stringify({ error: 'Not found' }), { status: 404 })
}
Decision: CORRECT Genuine IDOR vulnerability. Fix is internal to the edge function with no UX impact. Priority: high — prevents cross-tenant phishing.
CR-02
xero-payslips endpoint missing admin/hr role check — salary data exposure Needs Fix
supabase/functions/xero-payslips/index.ts : line 28
CodeRabbit finding

The authorisation check accepts any active company_users row regardless of role. The response contains complete payroll data: employee names, emails, gross pay, net pay, PAYE, NI, student loan, and pension amounts. Any ordinary employee can POST their company_id and read every colleague's salary. The xero-connect endpoint already restricts to admin and hr roles.

Validation

Confirmed — issue exists in current code. The xero-payslips/index.ts checks if (!cu) but does not check cu.role. The sister endpoint xero-connect/index.ts already has the correct pattern: cu.role !== 'admin' && cu.role !== 'hr'.

UX / service impact

UX impact: none. Only admin/HR users access the Xero payslips page in the UI. Adding the server-side role check matches the existing client-side routing guard.

Service impact: critical fix. Prevents any employee from reading salary data for the entire company. This is a GDPR Article 5 proportionality issue (financial PII accessible beyond the minimum necessary).

Proposed fix
// Add role check matching xero-connect pattern
if (!cu || (cu.role !== 'admin' && cu.role !== 'hr')) {
  return json({ error: 'Access denied' }, 403)
}
Decision: CORRECT One-line fix. Salary data exposure to all employees is a critical privacy issue. No UX impact — the admin panel already gates the page client-side. Priority: high.
CR-07
anonymise_employee uses wrong column names — GDPR erasure fails silently Needs Fix
supabase/migrations/047_gdpr_compliance.sql : line 460
CodeRabbit finding

The anonymise_employee function references columns that don't exist: given_by/given_to on kudos (actual: from_employee_id/to_employee_id), user_id on notifications (actual: employee_id), and booked_by on space_bookings (actual: employee_id). The function will error on first invocation, rolling back the entire erasure transaction.

Validation

Confirmed — issue exists in current code. Checked the current table schemas: kudos has from_employee_id and to_employee_id; notifications and space_bookings both use employee_id. The function has never been successfully invoked with data in these tables.

UX / service impact

UX impact: the GDPR erasure button in the admin panel will fail for any employee who has kudos, notifications, or space bookings. The error is caught and shown to the admin as a generic failure.

Service impact: GDPR Article 17 compliance failure. The right to erasure cannot be fulfilled. This is a launch blocker for any company processing EU personal data.

Proposed fix

Create a new migration to recreate anonymise_employee with corrected column names:

DELETE FROM kudos         WHERE from_employee_id = p_employee_id
                             OR to_employee_id = p_employee_id;
DELETE FROM notifications WHERE employee_id = p_employee_id;
DELETE FROM space_bookings WHERE employee_id = p_employee_id;
Decision: CORRECT GDPR erasure is non-functional. Must fix before any production erasure request is received. Priority: critical — SMB launch blocker.
CR-08
AUTO_PURGE missing from audit constraint — automated retention purge fails Needs Fix
supabase/migrations/057_medium_security_fixes.sql : line 270
CodeRabbit finding

The purge_expired_frozen_employees() function records AUTO_PURGE as the action type, but the gdpr_audit_logs_action_check constraint (updated in migration 070) only allows the existing actions plus SELF_GRANT_ACCESS. The audit INSERT fails, preventing the DELETE from executing, so expired frozen employees are never automatically purged.

Validation

Confirmed — issue exists in current code. Migration 070 defines the constraint as CHECK (action IN ('EXPORT', 'VIEW_PII', 'ANONYMISE', 'GRANT_ACCESS', 'REVOKE_ACCESS', 'SELF_GRANT_ACCESS')). AUTO_PURGE is not in the list. The pg_cron job will silently fail on every scheduled run.

UX / service impact

UX impact: none visible. The auto-purge runs as a background cron job. Admins won't see an error, but frozen employees past the retention period will remain in the database indefinitely.

Service impact: data retention non-compliance. GDPR Article 5(1)(e) requires storage limitation. If companies set a retention period, expired data must actually be purged. Without this fix, the retention policy is cosmetic only.

Proposed fix

Create a migration to update the constraint:

ALTER TABLE gdpr_audit_logs
  DROP CONSTRAINT gdpr_audit_logs_action_check;
ALTER TABLE gdpr_audit_logs
  ADD CONSTRAINT gdpr_audit_logs_action_check
  CHECK (action IN (
    'EXPORT', 'VIEW_PII', 'ANONYMISE',
    'GRANT_ACCESS', 'REVOKE_ACCESS',
    'SELF_GRANT_ACCESS', 'AUTO_PURGE'
  ));
Decision: CORRECT Data retention automation is broken. Quick constraint update. Priority: high — SMB launch blocker (data retention is a gate).
CR-12
Wrong column r.checkin_id in export_company_data breaks cancellation export Needs Fix
supabase/migrations/095_cancellation.sql : line 431
CodeRabbit finding

The break_records table defines checkin_record_id (from migration 083), not checkin_id. The export_company_data function references r.checkin_id, which will raise column r.checkin_id does not exist at execution time, failing the entire cancellation data export.

Validation

Confirmed — issue exists in current code. Checked migration 083: break_records has checkin_record_id uuid REFERENCES checkin_records(id). The export query in 095 uses the wrong column name. Additionally, CodeRabbit suggests using r.company_id = p_company_id instead, since break_records has its own company_id column, which is simpler and avoids the subquery entirely.

UX / service impact

UX impact: company data export fails during the cancellation flow when a company has break records. The super admin sees an error when trying to export company data before deletion.

Service impact: cancellation data archive is incomplete. Without the fix, the company's break records are not included in the pre-deletion export archive.

Proposed fix

Use the direct company_id filter instead of the broken subquery:

-- Replace:
'break_records', COALESCE((SELECT jsonb_agg(to_jsonb(r))
  FROM break_records r
  WHERE r.checkin_id IN (SELECT id FROM checkin_records
    WHERE company_id = p_company_id)), '[]'::jsonb)

-- With:
'break_records', COALESCE((SELECT jsonb_agg(to_jsonb(r))
  FROM break_records r
  WHERE r.company_id = p_company_id), '[]'::jsonb)
Decision: CORRECT Export function is broken. Simple column reference fix. Priority: medium — affects cancellation workflow only.

The SECURITY DEFINER functions export_employee_data and anonymise_employee check is_my_company(v_company_id) OR is_super_admin() but never verify the caller is the target employee or an admin. CR-11
app_settings SELECT USING(true) — cross-tenant settings readable Needs Validation
supabase/migrations/093_security_audit_fixes.sql : line 86
CodeRabbit finding

The app_settings SELECT policy uses USING(true), so any authenticated user can read every tenant's settings. The UPDATE policy checks only is_company_admin() without is_my_company(company_id), so an admin of Company A can update Company B's settings.

Validation

Needs investigation. Check what data app_settings contains. If it stores only feature flags and non-sensitive configuration (locale, date format, enabled modules), cross-tenant read may be low-risk. If it contains company-specific secrets, API keys, or business-sensitive thresholds, it needs scoping.

UX / service impact

UX impact of fix: none. Each company reads only its own settings row. The app already queries by company_id from context.

Service impact: depends on data sensitivity. The UPDATE cross-tenant write is definitely a bug regardless of data sensitivity — one admin should not modify another company's settings.

Proposed fix
-- SELECT: scope to own company
CREATE POLICY "Authenticated users can read app_settings"
  ON app_settings FOR SELECT TO authenticated
  USING (is_my_company(company_id) OR is_super_admin());

-- UPDATE: scope to own company + admin
CREATE POLICY "Admins can update app_settings"
  ON app_settings FOR UPDATE TO authenticated
  USING ((is_my_company(company_id) AND is_company_admin())
         OR is_super_admin());
Decision: PENDING VALIDATION Cross-tenant UPDATE is confirmed as a bug to fix. Cross-tenant SELECT risk depends on what the table stores. Validate table contents, then apply company-scoped policies to both. Priority: medium.
