Your questions answered

Can company admins see salaries? Do I need a dedicated payroll role?
Yes, this is a gap. Right now, every employee in a company can SELECT all salary data at the database level — the RLS policy is company-scoped, not role-scoped. The admin portal roles system gates the Payroll page in the UI, but the database doesn't enforce it. You need RLS-level salary isolation: only the employee themselves, plus users with a "payroll" portal permission, should be able to read salary/bank columns. This is Phase 2, item 2.1 below.
Is the 48-hour service admin access GDPR compliant?
Time-limited access is good practice, but self-granting is the problem. Under GDPR Art. 28, the processor (you) should only access controller (customer) data on documented instructions. The current ensure_super_admin_access() lets you self-grant access with no customer approval. For compliance, company admins should grant/approve access, not the service admin. The 48-hour window itself is fine — it's the consent flow that needs fixing. Phase 2, item 2.3.
As the service provider, I have full database access — is this allowed?
Yes, but only with a signed DPA and documented controls. GDPR allows processors to access personal data — that's the whole point of a Data Processing Agreement. Your DPA must state: what data you access, why, your security measures, your sub-processors (Supabase, Cloudflare, Brevo), and breach notification obligations. Supabase service role key access is normal for a SaaS operator. Document it, don't remove it. Phase 1, item 1.2.
Do I need to check where code is hosted and what backups I get?
Yes — you need to document this and verify it. Your Supabase project region determines where employee data is stored. Check your Supabase dashboard for the region (it should be EU/UK for GDPR). Cloudflare Pages runs on their global CDN but the SPA contains no PII — only the Supabase database holds personal data. Supabase Pro includes daily backups with 7-day PITR. You need to test a restore and document the process. Phase 3, items 3.2 and 3.3.

PHASE 2 RBAC and Access Controls Week 2–3 · £0 engineering
2.1 Salary and payroll data isolation GAP DECISION

Current state

Critical gap. The employees table RLS SELECT policy (can_access_company(company_id)) grants read access to ALL employees in the company — including salary, bank details, NI number, and tax code. Any authenticated employee can query these columns directly via the Supabase API, even though the UI only shows them on admin pages.

The admin portal roles system gates the Payroll page but this is UI-only. The accounting portal role can be configured with payroll access, but the database doesn't enforce it.

Similarly, payslips are readable by all company members at the RLS level — the employee page filters by employee_id in the UI query, but RLS allows reading anyone's payslips.

What's needed

  • Create a database view or RLS policy that strips salary/bank/NI columns from SELECT unless the user has payroll access or is reading their own record
  • Options:
    • Option A — Column-level security via views: Create an employees_safe view that excludes sensitive columns, grant employees SELECT on the view only. Payroll-permissioned users query the full table.
    • Option B — RLS with column masking: Keep one table but use a helper function has_payroll_access(company_id) that checks the user's portal role. Return NULL for salary/bank columns when the user lacks payroll access and isn't reading their own row.
  • Lock down payslips RLS: employees can only SELECT their own payslips

Recommendation

Option B is simpler and doesn't require frontend migration. A new has_payroll_access() function checks admin_portal_access for the payroll feature, and the RLS policy uses it to mask sensitive columns.

1–2 days engineering

2.3 Service admin access — fix self-grant GAP DECISION

Current state

The ensure_super_admin_access() function lets the super admin self-grant 48-hour access to any company's PII data. The 48-hour time limit is good. The three-tier access model (PII gated, config always, partial HR) is good. The GDPR audit logging is good.

The problem: granted_by and granted_to are both the super admin's own ID. Under GDPR Art. 28, the controller (company admin) should authorise processor access, not the processor themselves.

What's needed

  • Option A — Company admin approval flow: Super admin requests access → company admin gets a notification → approves/denies → access granted for 48 hours. Most GDPR-compliant.
  • Option B — Company admin pre-authorisation: During onboarding, company admin ticks "Allow InflowHR support access when needed" with configurable scope. Self-grant then has documented consent.
  • Option C — Keep self-grant but document in DPA: The DPA explicitly states that the processor may access data for support purposes. Less ideal but legally defensible with the audit trail you already have.

Recommendation

Option B is the pragmatic choice for SMB. Pre-authorisation during onboarding plus audit logging is compliant and doesn't create friction. Include a toggle in company settings to revoke/re-grant.

1 day engineering

PHASE 3 Infrastructure Verification Week 3 · £0
3.1 Encryption at rest and in transit DONE

Current state

Platform-level encryption is in place. Supabase provides AES-256 encryption at rest for the database and TLS 1.2+ in transit. Cloudflare enforces HTTPS for the frontend. This is sufficient for SMB.

Note on field-level encryption

Bank details, NI numbers, and tax codes are stored as plaintext columns. Field-level encryption (using pgcrypto) would add a layer but complicates queries and isn't required for GDPR compliance — AES-256 disk encryption satisfies the "appropriate technical measures" requirement. The existing column masking in the admin UI (SEC-H05) prevents casual viewing.

no action needed for SMB launch
3.2 Data hosting location VERIFY

Current state

The Supabase project region is set at project creation and isn't stored in the local config. You need to verify this in the Supabase dashboard. For UK/EU customers, the database should be in an EU region (eu-west-1 London, eu-west-2, or eu-central-1 Frankfurt).

What to check

  • Supabase Dashboard → Project Settings → General → Region
  • Cloudflare Pages: the SPA is served from Cloudflare's global CDN — this is fine as the SPA contains no PII (all PII lives in Supabase)
  • Brevo (email): check their data processing region — they offer EU hosting

What to document

Your privacy notice needs to state: "Employee data is stored on servers in [region] operated by Supabase (our sub-processor). Application delivery uses Cloudflare's global CDN for static assets only — no personal data is cached at the edge."

30 min verification

3.4 Security headers — add HSTS GAP

Current state

Comprehensive security headers are configured in public/_headers: X-Frame-Options, X-Content-Type-Options, Referrer-Policy, Permissions-Policy, CSP, X-XSS-Protection. Missing: Strict-Transport-Security (HSTS).

What's needed

4.3 Special category data — religion field GAP DECISION

Current state

The religion column exists on both employees and onboarding tables. Religion is GDPR Article 9 special category data — it requires explicit consent (Art. 9(2)(a)) or a specific employment law exemption (Art. 9(2)(b)).

Options

  • Option A — Remove it: Simplest. Most UK SMBs don't need this field. Drop the column from both tables.
  • Option B — Keep with explicit consent: Add a consent checkbox specifically for religion data collection, with a clear explanation of why it's collected (e.g., accommodating religious holidays). Track the consent in an employee_consents table.
  • Option C — Make it optional and company-configurable: Add it as a feature toggle. Companies that need it enable it and accept responsibility for the lawful basis.
